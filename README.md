# HW Checker Bot

Telegram-бот для сдачи домашних заданий студентами и приёма обращений в техподдержку. Работает на long-polling, хранит данные в двух базах данных на SQLite, одна из них - выгрузка из 1С.

## Возможности

| Раздел | Что делает |
|---|---|
| 🔐 **Вход** | Привязка Telegram-аккаунта к студенту по персональному коду из выгрузки 1С. Запрос кода в поддержку, если кода нет. |
| 📚 **Домашнее задание** | Предметы → темы → сдача файла. Валидация расширения и размера, лимит попыток на тему. |
| 📊 **Мои сдачи** | Прогресс по всем темам: что сдано, что нет, сколько попыток использовано. |
| 👤 **Профиль** | Имя, группа, поток, персональный код. Выход из аккаунта. |
| ✨ **Что нового** | Темы с ДЗ, появившиеся в выгрузке после прошлого запуска бота. |
| 🤝 **Помощь** | Обращения в поддержку (баг / идея / проблема с ДЗ / другое) текстом, файлом или фото. Справка по боту. |

**Профиль нагрузки:** до ~20 одновременных пользователей. Без очередей, микросервисов и лишней инфраструктуры.

**Правила сдачи (по умолчанию):**
- один файл за раз;
- до **20 МБ**;
- форматы: `pdf`, `doc`, `docx`, `xls`, `xlsx`, `zip`, `rar`, `7z`;
- до **3 попыток** на тему.

Все лимиты настраиваются через переменные окружения (.env).

## Как все работает

Бот читает две базы:

| База | Режим | Источник | Что внутри |
|---|---|---|---|
| `snapshot.db` | read-only | выгрузка из 1С | студенты, группы, потоки, предметы, темы |
| `storage.db` | read-write | создаёт сам бот | аккаунты, сдачи, новости |

`snapshot.db` **не создаётся ботом**: если файла нет — приложение падает на старте с понятной ошибкой. Обновление snapshot — задача администратора (см. [Обновление snapshot](#обновление-snapshot-из-1с)).

`storage.db` мигрируется автоматически при старте. Миграции вшиты в бинарник через `embed.FS` — отдельная папка `migrations/` для деплоя не нужна.

Состояние диалогов (кто вводит код, кто ждёт файл) хранится **в памяти** и сбрасывается при перезапуске. Это осознанно: аккаунт лежит в `storage.db`, файлы — на диске, потеря режима — не потеря данных.

**Слои приложения:** `handler → service → repository / storage`. Каждый слой знает только свой уровень, общение — через интерфейсы, объявленные у потребителя (`internal/service/ports.go`).

### Что происходит при старте

1. Читается `.env` из рабочей директории (если есть).
2. Валидируется конфиг (`TELEGRAM_TOKEN`, пути к базам).
3. Создаётся HTTP-клиент (с прокси, если задан `PROXY_URL`).
4. Применяются миграции `storage.db` (вшиты в бинарник).
5. Открываются обе базы. `snapshot.db` — строго read-only.
6. Проверяется свежесть `snapshot.db` — если старше `SNAPSHOT_MAX_AGE_HOURS`, пишется Warn (бот не падает).
7. Собираются репозитории, сервис, обработчики, регистрируются команды.
8. Синхронизируются новости: новые темы с ДЗ попадают в `news`.
9. Запускается long-polling.

### Что происходит при остановке (Ctrl+C или закрытие окна)

Реализован небольшой graceful shutdown:

1. Long-polling прекращается.
2. Обработчики, которые уже в работе (скачивание файла, запись сдачи), **дожидаются завершения** — до 60 секунд. Это реализовано через `drainMiddleware` (`internal/handler/middleware.go`): каждый обработчик учитывается в `sync.WaitGroup`, а `context.WithoutCancel` не даёт родительскому контексту оборвать уже начатую работу.
3. По истечении таймаута или после завершения всех обработчиков закрываются idle-соединения HTTP-клиента и обе базы.

Если в момент остановки пользователь сдавал большой файл — обработчик доработает в пределах 60 секунд. Дольше ждать нельзя: на практике это означает «не выключай бота, пока он не сказал "бот остановлен"».

## Запуск через Makefile

`Makefile` в корне проекта — тонкая обёртка над `go run`, `go build`, `go test`. Он **опционален**: всё то же самое можно делать руками. Но с ним короче и меньше шансов забыть флаг (`-race`, `-trimpath`, `-ldflags`).

### Требования

- **make** для Windows: [`mingw32-make`](https://www.mingw-w64.org/downloads/) из MinGW-w64, либо [`make`](https://gnuwin32.sourceforge.net/packages/make.htm) из GnuWin32, либо `make` из WSL/Git Bash. Главное — чтобы `make` был в `PATH`.
- Если `make` нет — используйте `go run` / `go build` напрямую, команды ниже показывают эквиваленты.

### Команды

| Команда | Что делает | Эквивалент без make |
|---|---|---|
| `make run` | Запускает бота из исходников | `go run ./cmd/bot` |
| `make check` | Быстрая проверка: `go build ./...` + `go vet ./...` | `go build ./... && go vet ./...` |
| `make build` | Собирает `bin\hw-checker.exe` (сначала вызывает `check`) | `go build -trimpath -ldflags "-s -w" -o bin/hw-checker.exe ./cmd/bot` |
| `make test` | Тесты с `-race -count=1 -timeout 60s` | `go test ./internal/... -race -count=1 -timeout 60s` |
| `make test-v` | То же, но verbose | `go test ./internal/... -race -count=1 -timeout 60s -v` |
| `make clean` | Удаляет `bin\` | `rmdir /s /q bin` (или удалить папку вручную) |
| `make tidy` | `go mod tidy` | `go mod tidy` |
| `make fmt` | `goimports -w .` (см. ниже) | `goimports -w .` |
| `make fix` | `tidy` + `fmt` | `go mod tidy && goimports -w .` |

### Что важно знать

- **`.env` подхватывается автоматически.** `Makefile` содержит `-include .env` и `export` — все переменные из `.env` попадают в окружение `make run` и `make test`. Отдельно `export`-ить ничего не надо.
- **`make build` сначала вызывает `make check`.** Не собираем заведомо сломанный код: если `go vet` или `go build ./...` падают — бинарник не появится.
- **`TEST_PKGS` — явный список пакетов.** В `Makefile` перечислены пакеты, где есть тесты (`config`, `database`, `network`, `ratelimit`, `repository`, `service`, `session`, `storage`, `utils`). Это сделано, чтобы в выводе `make test` не было `[no test files]`. **Если добавляете тесты в новый пакет — допишите его в `TEST_PKGS`.**
- **`make fmt` требует `goimports`.** Устанавливается один раз:
  ```cmd
  go install golang.org/x/tools/cmd/goimports@latest

## Конфигурация

Все настройки читаются из переменных окружения. `.env` подхватывается автоматически, если лежит в рабочей директории. Отсутствие `.env` — не ошибка: переменные могут быть заданы в системе.

### Telegram

| Переменная | Обязательна | По умолчанию | Описание |
|---|---|---|---|
| `TELEGRAM_TOKEN` | **да** | — | Токен бота. Без него `Validate()` вернёт ошибку. |
| `PROXY_URL` | нет | пусто | SOCKS5/HTTP-прокси. Пример: `socks5://127.0.0.1:9150` (Tor Browser). |

### Логирование

| Переменная | По умолчанию | Описание |
|---|---|---|
| `APP_ENV` | `production` | `production` — JSON, `development` — цветной console. |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error`. |
| `LOG_ENABLED` | `true` | Писать логи в файл (в stdout — всегда). |
| `LOG_DIR` | `data/logs` | Каталог логов. |
| `LOG_MAX_SIZE_MB` | `10` | Размер файла до ротации. |
| `LOG_MAX_FILES` | `7` | Сколько файлов хранить. |
| `LOG_MAX_AGE_DAYS` | `30` | Удалять старше N дней. |
| `LOG_COMPRESS` | `true` | Сжимать закрытые логи gzip. |

### Базы

| Переменная | По умолчанию | Описание |
|---|---|---|
| `SNAPSHOT_DB_PATH` | `data/snapshot.db` | Выгрузка 1С (read-only, файл должен существовать). |
| `STORAGE_DB_PATH` | `data/storage.db` | База бота (создаётся автоматически). |
| `SNAPSHOT_MAX_AGE_HOURS` | `72` | Через сколько часов без обновления snapshot.db считается устаревшим. `0` — отключить проверку. Бот не падает, только Warn при старте. |

### Файлы и лимиты

| Переменная | По умолчанию | Описание |
|---|---|---|
| `UPLOADS_DIR` | `data/uploads/` | Корень для сдач и обращений. |
| `MAX_FILE_SIZE_MB` | `20` | Максимальный размер файла. |
| `ALLOWED_FILE_EXTS` | `pdf,doc,docx,xls,xlsx,zip,rar,7z` | Расширения через запятую (нормализуются к lowercase). |
| `MAX_SUBMISSIONS_PER_THEME` | `3` | Попыток на одну тему. |

**Некорректные значения.** Числа и bool, которые не парсятся или ≤ 0, молча откатываются к дефолту. `ALLOWED_FILE_EXTS=,,,` эквивалентна отсутствию переменной. Это защищает от опечаток при деплое.

**Прокси.** Если Telegram недоступен напрямую, поднимите Tor Browser или другой SOCKS5 и задайте `PROXY_URL`. Отдельного health-check при старте нет: первая сетевая ошибка всплывёт на первом `getUpdates` и будет залогирована как `Warn «сеть недоступна, переподключаемся»` — это нормально, библиотека сама переподключается.

## Раскладка файлов на диске

### Сдачи

```text
<UPLOADS_DIR>/homework/<Группа>/<Код_темы Название>/<ts>_v<N>_<ФИО>_<код>.<ext>
```

Пример:

```text
data/uploads/homework/ПИ-21/T-1 Введение/2026-10-10_15-04-05_v1_Иванов_Иван_CODE1.pdf
```

Имена санитизируются: запрещённые для Windows символы заменяются на `_`, длина ограничена.

### Заявки на код и поддержка

```text
support/login/<YYYY-MM-DD>/tg<telegram_id>.txt
support/<reason>/<ts>_tg<id>/info.txt
support/<reason>/<ts>_tg<id>/<файл>
```

Причины (`reason`): `bug`, `ideas`, `homework`, `other`. Администратор смотрит эти папки вручную — бот только пишет файлы.

## Ограничения UX

Намеренные решения, зафиксированные в коде:

- **Альбомы (media group) не принимаются.** Telegram шлёт каждый файл отдельным апдейтом, и пользователь может подумать, что все файлы сохранятся. В ответ бот удаляет сообщение и подсказывает отправить один файл или архив.
- **Фото в ДЗ отклоняются.** Сдавать можно только **документом** — это гарантирует имя файла и предсказуемое расширение.
- **В режиме ввода кода команды игнорируются.** Выйти можно только кнопкой «Назад».
- **Состояние диалога в памяти.** После перезапуска пользователи начинают с начала — это ок, аккаунт и файлы сохранены.
- **Заявка на код активна 30 дней.** Пока заявка не истекла, повторное нажатие «Запросить код» возвращает «Заявка уже отправлена». TTL дисковый — считается по дате папки и mtime файла, поэтому перезапуск бота на него не влияет. Если админ не ответил за 30 дней — студент может запросить повторно.

## Остановка и перезапуск

Бот слушает `SIGINT` и `SIGTERM`. На Windows это соответствует:

- **Ctrl+C** в консоли;
- **закрытие окна** консоли (если запущено через `cmd` / PowerShell, отправляется `SIGTERM`-эквивалент);
- **завершение процесса** через Диспетчер задач (жёсткое, без graceful shutdown — не рекомендуется).

При корректной остановке:

1. Long-polling прекращается.
2. Обработчики, которые уже в работе, дожидаются завершения (до 60 с).
3. Закрываются соединения и обе базы.

В логах:

```
INFO  ожидаю завершения обработчиков, прерывать нельзя (макс ждем 60 сек)  {"active": 1}
INFO  все обработчики завершены
INFO  бот остановлен
```

**Перезапуск:** состояния диалогов (ожидание кода/файла) сбрасываются — это нормально. Аккаунты и сдачи живут в `storage.db` и на диске и не теряются.

## Обновление snapshot из 1С

`snapshot.db` — read-only выгрузка. Бот её не трогает.

**Порядок обновления:**

1. Остановить бота (Ctrl+C в консоли или закрыть окно).
2. Заменить файл (лучше через `move`, не in-place):
   ```cmd
   move C:\path\to\new-snapshot.db data\snapshot.db
   ```
3. Убедиться, что файл читается и у бота есть права:
   ```cmd
   sqlite3 data\snapshot.db "SELECT COUNT(*) FROM students;"
   ```
4. Запустить: `bin\hw-checker.exe`.

**Что произойдёт автоматически:**

- При старте `SyncNews` сравнит темы `has_homework = 1` со своими `seen_themes`: новые попадут в `news`, исчезнувшие — удалятся.
- Возраст snapshot логируется при открытии (`updated_at` и `age`) — по логам видно свежесть.

**Если темы «пересоздались»** (сменились коды) — старые записи в `submissions` останутся со старыми `theme_code`, экран «Мои сдачи» их не покажет. Связь сдачи и темы держится на коде темы — при необходимости мигрируйте коды на стороне 1С, чтобы они не менялись.

## Troubleshooting

### `409 Conflict: can't use getUpdates method while webhook is active`

У токена остался установленный webhook от другого бота или инстанса. Снять вручную:

```cmd
curl "https://api.telegram.org/bot<TOKEN>/deleteWebhook?drop_pending_updates=false"
```

### `config: TELEGRAM_TOKEN не задан`

Нет `.env` с токеном и переменная не задана в системе. Создайте `.env` или задайте `TELEGRAM_TOKEN`.

### `snapshot: файл не найден (сделайте выгрузку из 1С)`

`data\snapshot.db` отсутствует. Скопируйте выгрузку по пути `SNAPSHOT_DB_PATH`.

### `no such host`, `connection refused`, `i/o timeout`

Telegram недоступен напрямую. Варианты:

1. **Tor Browser** запущен — задайте `PROXY_URL=socks5://127.0.0.1:9150` (не `9050` — это для системного Tor).
2. **Системный VPN** — оставьте `PROXY_URL` пустым.
3. **Свой SOCKS5** — укажите адрес.

Проверить: `curl --socks5 127.0.0.1:9150 https://api.telegram.org`. В логе будут периодические `Warn «сеть недоступна, переподключаемся»` — это норма, библиотека сама переподключается. Бот при сетевой ошибке **не падает**.

### `лог в файл отключён: нет прав на запись`

`LOG_DIR` недоступен. Проверьте права или задайте `LOG_ENABLED=false`.

### Файлы не принимаются, «Неверный формат»

Проверьте `ALLOWED_FILE_EXTS` и `MAX_FILE_SIZE_MB`. Файл должен отправляться **документом**, не альбомом и не фото.

### «Слишком много попыток» при входе

Лимитер — 10 попыток/мин на пользователя (fixed window, in-memory). Сбрасывается после успешного входа. Чтобы изменить — `loginAttemptsPerMinute` в `cmd/bot/main.go`.

### «Заявка уже отправлена» при запросе кода

Заявка на код активна **30 дней** с момента создания (`loginRequestTTL` в `internal/storage/files.go`). Всё это время повторное нажатие «Запросить код» возвращает «Заявка уже отправлена». По истечении 30 дней студент может запросить код повторно — старый файл игнорируется.

TTL **дисковый**: считается по дате папки и mtime файла в `support/login/<YYYY-MM-DD>/tg<ID>.txt`, поэтому **перезапуск бота на него не влияет**. Если бот перезапускается каждый день — TTL всё равно работает корректно.

Если админ не отвечает быстро и 30 дней кажутся долгими — уменьшите константу до `3 * 24 * time.Hour` или `24 * time.Hour`.

### `message is not modified` в логах

Не ошибка: Telegram так отвечает, когда текст или разметка совпадают с уже показанным. `editMessage` её гасит.

### Стейл-аккаунт (студент пропал из выгрузки)

`CurrentStudent` при `ErrNotFound` от `students.GetByPersonalCode` удаляет привязку и возвращает `ErrNotFound` — пользователю покажется экран входа.

### Бот «зависает» на одном пользователе

Проверьте логи с `LOG_LEVEL=debug`: возможно, `downloadFile` ждёт ответа от Telegram. Общий таймаут HTTP-клиента — 300 секунд. Для медленного канала 20 МБ могут не успеть. Уменьшите `MAX_FILE_SIZE_MB` или попросите сжать файл.

### Сообщения не удаляются из чата

`deleteMessage` пишет только в Debug — не критично. Telegram не даёт удалять сообщения старше 48 часов и ограничивает права бота в группах.

## Безопасность

- **Токен** — только из env. `.env`, `*.db`, `/data`, `/scripts`, `/bin` в `.gitignore`.
- **Персональный код** — сообщение с кодом удаляется из чата после обработки.
- **Rate limit на вход** — 10 попыток/мин на пользователя, in-memory.
- **Ограничение запросов кода** — один активный запрос на пользователя за 30 дней (`loginRequestTTL`). Защита от спама кнопкой и от перегрузки админа. TTL проверяется по дате файла на диске — перезапуск не обнуляет.
- **Файлы** — белый список расширений, лимит размера, atomic write (temp + rename), откат файла при ошибке записи в БД.
- **Snapshot** открыт read-only — бот не может изменить выгрузку 1С.
- **Graceful shutdown** — начатые обработчики дорабатывают, данные не теряются при штатной остановке.
